# JIB — البنية التقنية

## التطبيقات
- `apps/customer`: تطبيق Flutter للزبون.
- `apps/merchant`: تطبيق Flutter للتاجر.
- `apps/courier`: تطبيق Flutter للمندوب.
- `apps/admin`: تطبيق Next.js مستقل باسم **JIB Manager**. يبقى المسار كما هو حتى لا تنكسر إعدادات Vercel الحالية.
- `supabase/migrations`: مخطط قاعدة البيانات وسياسات الأمان والإجراءات المخزنة.
- `docs`: المواصفات وخطة التنفيذ والمراجعات.

## الخدمات
- GitHub: المصدر وإدارة الفروع ومراجعة التغييرات.
- GitHub Actions: بناء واختبارات الويب وFlutter.
- Supabase: Auth وPostgreSQL وRLS وStorage وRealtime وRPC.
- Vercel: استضافة JIB Manager المستقل.
- Render: خدمات خلفية/عمال مهام عند الحاجة وبعد إعدادها والتحقق منها.
- Firebase Cloud Messaging: إشعارات الهاتف بعد إعداد المشروع ومفاتيح الخدمة.
- مزود خرائط ورسائل ومكالمات ودفع: يختار ويُفعّل بعقود ومفاتيح مقيدة؛ لا يُفترض أنه متصل قبل اختبار فعلي.

## JIB Manager
JIB Manager تطبيق إدارة مستقل عن تطبيقات الهاتف، لكنه يتصل بقاعدة JIB نفسها. كل مسار محمي يتحقق من جلسة Supabase ودور admin في الخادم. لا تُستخدم مفاتيح service-role في المتصفح. العمليات الحساسة تنفذ عبر RPC تتحقق من المدير وتسجل في سجل تدقيق.

## إعدادات التنفيذ والولاء لكل فرع

- جدول `store_branch_policies` يربط إعدادات التشغيل بسجل الفرع `stores.id`، وليس بالعلامة التجارية العامة. صلاحية القراءة والكتابة إدارية فقط عبر RLS.
- تدعم السياسة حالات `pending` و`approved` و`rejected` و`suspended`؛ لا يلزم أن يكون الفرع معتمداً عند حفظ الطلب الأولي للموافقة. أما اختيار `approved` فيتطلب مرجع موافقة وبيانات المدير والتوقيت.
- لا يُسمح باختيار `jib_central_order` أو `store_digital_order` أو `partner_api_pos` دون موافقة صريحة للفرع؛ ويتطلب نمط القناة الرقمية رابط HTTPS، ويتطلب API/POS اتصال تكامل فعلي.
- لا يُسمح باستخدام `jib_business_account` أو `partner_business_account` دون موافقة برنامج الولاء وتحديد اسمه.
- دالة `checkout_order` هي مصدر الحقيقة: تقرأ سياسة الفرع داخل المعاملة وتنسخ طريقة التنفيذ ونمط الولاء واسم البرنامج إلى أعمدة snapshot على الطلب. لا يعتمد القرار على قيمة يرسلها تطبيق الزبون.
- لا تخزن جداول السياسات أي كلمات مرور أو مفاتيح API أو أرقام عضوية سرية. يتم حفظ رموز الوصول حصراً في مخزن أسرار عند بناء التكامل الرسمي.
- وجود إعداد موافقة لا يساوي إرسال طلب خارجي ولا إضافة نقاط فعلية؛ الطابور التشغيلي لتقديم الطلب، ومهام الشراء/الاستلام الخاصة بالمندوب، ودفتر معاملات النقاط تحتاج تكملة واختباراً مستقلاً قبل تشغيلها.

## مبادئ الأمان والتشغيل
- أقل صلاحية لازمة، وRLS على جميع جداول المستخدمين.
- الأسعار وحالات الطلب والإسناد تتحقق في قاعدة البيانات، لا في واجهة العميل فقط.
- كل انتقال حالة مهم يسجل actor وstatus وtimestamp وسبباً عند الحاجة.
- بيانات الموقع والاتصال لا تظهر إلا للمشارك المصرح وفي الوقت المناسب.
- أسرار الخدمات في متغيرات بيئة محمية فقط.
- إجراءات الذكاء الاصطناعي لا تنفذ تغييرات مالية أو صلاحيات أو حذفاً أو نشر إنتاج دون موافقة بشرية.
- لا يعلن عن خدمة أو ميزة بأنها فعالة حتى ينجح اختبار تكامل حقيقي.

## قرارات تنتظر الاعتماد
- حدود مناطق التوصيل في الرباط ورسوم كل منطقة والحد الأدنى والعمولة.
- مزود الخرائط وسياسة دقة وتخزين الموقع.
- مزود SMS/WhatsApp/Voice ورسائل الموافقة والتكلفة.
- بوابة الدفع المغربية عند الانتقال من الدفع النقدي.
- سياسة الإلغاء والاسترداد والتسوية وحفظ السجلات.
- مفاتيح التوقيع وحسابات النشر القانونية.
